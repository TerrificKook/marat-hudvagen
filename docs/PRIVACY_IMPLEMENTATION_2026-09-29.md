# Проверка минимальной схемы: 29 сентября 2026

Название: техническое упрощение сайта.
Цель: сайт с прямыми контактами, без необязательной отправки данных посетителя.
Шаги: проверить исходники; удалить необязательный сбор; проверить страницы и передачу файлов.
Срок этой версии: 29 сентября 2026. Публикация после проверки владельцем.
Владелец технической приёмки: Динар. Действия от имени бизнеса выполняет его оператор.

## Границы готовности

Это технические изменения, не заключение о полном соблюдении 152-ФЗ.
На дату задания уведомление от маминого ИП в Роскомнадзор НЕ подавалось.
Правки не подают уведомление, не меняют DNS и хостинг, не передают права на домены,
не подтверждают место хранения писем и заказов, не удаляют исторические данные из кабинетов аналитики.

Публичные пояснения обновлены по фактам кода. До юридического завершения нужно подтвердить
оператора и его реквизиты/адрес, основания и сроки обработки обращений, почту и доступы,
местонахождение баз и журналов, подачу требуемого уведомления. Для чужого бизнеса
не подставлять мамино ИП автоматически. Не считать правила мессенджера заменой обязанностей получателя.
Приобретение российского хостинга само по себе не закрывает эти вопросы.

## Публикация на REG.RU

1. Проверить существующую услугу «Хостинг - 1»: тариф, статус, лимиты, SFTP/SSH.
2. Подтвердить у хостинга размещение услуги, журналов, резервных копий и почты в РФ.
3. Создать отдельный каталог и привязку для каждого домена; загрузить только публичный пакет.
4. Сначала проверить копию, ресурсы, контакты и HTTPS; затем менять адреса A/AAAA/CNAME.
   Сохранить MX, SPF, DKIM, DMARC и TXT-подтверждения. Не менять NS целиком без переноса зоны.
5. Регистратор может остаться прежним, включая Dynadot для dinar.agency.
6. После проверки новой публикации отключить прежний GitHub Pages и его деплой.
7. Исходники остаются в GitHub. Для автоматизации использовать сборку там и одностороннюю
   выгрузку публичных файлов через SFTP/SSH на REG.RU, без чтения почты, логов и клиентских данных.
   Закрытый ключ и проверенный ключ сервера хранить в Secrets, не в репозитории.
   Не использовать StrictHostKeyChecking=no; не синхронизировать с --delete корень всего хостинга.

Не покупать VPS/WordPress/базу MySQL ради этих статических сайтов. Не выгружать весь репозиторий:
.git, docs, notes, отчёты, исследования, инструкции и клиентские данные не являются публичным сайтом.

## Изменения этой копии

```json
{
  "notice_resources_removed": 14,
  "intake_forms_before": 0,
  "trackers_before": 0,
  "canonical_synced_to_existing_CNAME": "https://www.hudwagen.ru/"
}
```

Домен взят из существующего `CNAME`: `www.hudwagen.ru`, не выбран заново. Старая canonical-ссылка на GitHub Pages исправлена в генераторе и публичном корне. Настройки DNS и редирект с hudwagen.ru на www.hudwagen.ru этой правкой не меняются.

## Готовый механизм публикации (пока не настроен и не запущен)

`python3 tools/package_public.py` создаёт только публичную папку `dist-regru/`.
Workflow `deploy-regru.yml` запускается вручную и только из main. Пока переменная
`REGRU_DEPLOY_ENABLED` не равна `true`, публикация завершается без отправки файлов.
В Secrets требуются `REGRU_HOST`, `REGRU_USER`, `REGRU_PORT` (или 22),
`REGRU_REMOTE_PATH`, `REGRU_SSH_KEY`, `REGRU_KNOWN_HOSTS`.
Ключ сервера подтвердить у хостинга; приватный ключ сюда и в переписку не вставлять.
REG.RU должен подтвердить SSH и rsync для выбранной услуги.
Первую загрузку делать в пустой отдельный каталог сайта, проверить HTTPS и ссылки.
Автоматический запуск после push намеренно пока не включён.
После успешной ручной проверки можно добавить событие push только для main.
Workflow не использует --delete: старые ненужные файлы на сервере проверить отдельно.

Результат этой версии не утверждает, что уведомление РКН или юридическое оформление завершены.
